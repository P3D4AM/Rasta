# راهبرد تست رستا (Test Strategy)

> سند فاز ۵ — ۲۰۲۶-۱۰-۲۶. این سند «چگونه تست می‌کنیم» را تعریف می‌کند؛ فهرست دقیق تست‌ها در `test-inventory.md` و ماتریس رفتار در `docs/parity/apibaseinfo-matrix.md`.

## ۱) اصول

1. **شواهد قبل از تست، تست قبل از کد.** هر رفتار مورد انتظار باید از منبع معتبر (دیکامپایل / متن SP / satellite fa-IR / کاتالوگ data.zip) استخراج و در تست مستند شود؛ سپس پیاده‌سازی. الگوی کار: قرمز (تست از قرارداد) → سبز (پیاده‌سازی) — نمونهٔ کامل: `tests/integration/baseinfo-geo.test.ts`.
2. **صداقت وضعیت‌ها.** وضعیت‌ها: `NOT_ANALYZED / ANALYZED / IMPLEMENTED / TESTED / VERIFIED / BLOCKED`. `VERIFIED` فقط با اجرای موفق تستِ برخاسته از شواهد + تطبیق رفتار کامل (شامل UI) ثبت می‌شود. «کامپایل شد» یا «endpoint دارد» هیچ‌کدام VERIFIED نیست.
3. **ایزولاسیون کامل از دادهٔ واقعی.** تست‌ها هرگز به دیتابیس توسعه (`custom.db`)، سرویس پیامکی واقعی یا دادهٔ تولیدی دست نمی‌زنند:
   - تست واحد: بدون دیتابیس و بدون سرور.
   - تست یکپارچه‌سازی/E2E: SQLite آزمایشی تازه (`tests/.tmp/test.db`) که در هر اجرا از نو ساخته و seed می‌شود و در پایان حذف می‌شود؛ دستور آزمایشی هیچ‌وقت دیتابیس واقعی را پاک نمی‌کند.
4. **قطعیت و استقلال.** seed قطعی است (تاریخ‌های ثابت، کاربران با مجوز شناخته‌شده، دادهٔ جغرافیایی با روابط مشخص). تست‌ها به ترتیب اجرا یا دادهٔ باقی‌مانده از تست دیگر وابسته نیستند (هر فایل کلاینت HTTP خودش را می‌سازد؛ داده‌های وابسته در همان تست ساخته و پاک می‌شوند).
5. **قابلیت تکرار با یک دستور.** همه چیز از طریق اسکریپت‌های `package.json` اجرا می‌شود — بدون curl دستی و بدون سرورِ از پیش روشن‌شده توسط انسان.

## ۲) لایه‌ها و ابزارها

| لایه | ابزار | چه چیزی را می‌پوشاند | سرعت |
|---|---|---|---|
| واحد | **Vitest 5** (`test:unit`) | منطق خالص: ماتریس RBAC (`can`)، تقویم جلالی، اعتبارسنجی‌ها، نگاشت‌های قرارداد | ~۰.۵ ثانیه |
| یکپارچه‌سازی | **Vitest 5** + سرور واقعی (`test:integration`) | API واقعی روی HTTP: گارد ۴۰۱/۴۰۳، ورود/خروج/نشست، قرارداد CRUD تعاریف پایه (پیام‌ها، ممیزی، وابستگی حذف) | ~۱۵ ثانیه (شامل spawn سرور) |
| E2E مرورگر | **Playwright** + Chromium (`test:e2e`) | جریان‌های حیاتی UI: ورود، ریدایرکت، ریل منو، صفحات اصلی، ۴۰۳ API از مرورگر | ~۱ دقیقه |

## ۳) معماری تست یکپارچه‌سازی (نکات حیاتی محیط)

- **globalSetup** (`tests/helpers/global-setup.ts`): ساخت دیتابیس تازه (`prisma db push`) → seed قطعی (`tests/fixtures/seed-test.ts`) → spawn سرور `next dev` روی **پورت آزاد تصادفی** با `DATABASE_URL` و `AUTH_SECRET` آزمایشی → گرم‌کردن مسیرهای مورد تست (کامپایل on-demand) → در teardown: بستن درخت فرآیند، حذف دیتابیس و distDir و بازگرداندن `tsconfig.json`.
- **چرا `node` و نه `bun` برای سرور تست؟** موتور query پرایسما (ماژول نسخه‌دار `@prisma/client-<hash>`) زیر runtime بون resolve نمی‌شود و همهٔ مسیرها ۵۰۰ می‌گیرند — با `node node_modules/next/dist/bin/next dev` درست کار می‌کند. (کشف و رفع همین مسئله بخشی از کار این فاز بود.)
- **distDir یکتا-به-ازای-اجرای** (`.next-test-<pid>`): دو هدف — تداخل با سرور توسعهٔ روی `.next` نگذارد و قفل dev (`dev/lock`) بین اجراها گیر نکند.
- **انتقال پارامترها به تست‌ها**: `provide/inject` وی‌تست + fallback فایل `tests/.tmp/runtime.json` (پورت/راز).
- Playwright از همان خط لوله با `scripts/e2e-server.mjs` استفاده می‌کند (`webServer` در `playwright.config.ts`).

## ۴) کاربران و دادهٔ seed (قطعی)

| کاربر | رمز | مجوز | کاربرد |
|---|---|---|---|
| `admin` | `admin123` | `isAdmin` (همه‌چیز) | مسیرهای موفق |
| `operator` | `operator123` | frmHomePage + frmCompanyI(آمدن) + frmMain×actDefine{Country,Province,City} + frmDefine{Country,Province,City}×[actInsert,actPost,actEdit,actDelete] | کاربر عملیاتی با دسترسی تعاریف جغرافیایی |
| `viewer` | `viewer123` | فقط frmHomePage×actView | تست ۴۰۳ (نشست معتبر، مجوز ندار) |

دادهٔ جغرافیایی seed: ایران (کد ۹۸) با استان تهران (کد ۲۱) با شهر تهران؛ کشورِ تنها (۸۸۸) بدون هیچ وابستگی؛ کشور ۹۹۹ با «استان یتیم» بی‌شهر — هر ترکیب برای یک سناریوی حذف/وابستگی. تاریخ ثابت ۱۴۰۴/۰۷/۱۵.

## ۵) گیت‌های امنیتی که حتماً تست می‌شوند

1. **۴۰۱**: همهٔ مسیرهای محافظت‌شده بدون نشست (نمونه‌ها در `tests/integration/auth.test.ts` — الگو برای افزودن مسیرهای جدید).
2. **۴۰۳**: کاربر با نشست اما بدون مجوز فرم×اکشن (`tests/integration/guards.test.ts` + سنجش E2E از مرورگر).
3. **تفکیک دقیق فرم×اکشن**: داشتن actInsert ≠ داشتن actPost (الگوی گیت‌های خود CRMIdeal که ثبت با actPost است).
4. **کوکی نشست**: HttpOnly، باطل‌شدن پس از خروج.

## ۶) CI (GitHub Actions)

`.github/workflows/ci.yml` — چهار کار موازی روی هر push/PR به develop و main:
1. `quality`: typecheck (tsc --noEmit) + lint + تست واحد
2. `integration`: تست یکپارچه‌سازی (spawn سرور داخل خود تست)
3. `e2e`: Playwright + Chromium (آپلود artifacts در صورت شکست)
4. `build`: بیلد standalone با دیتابیس موقت

> وضعیت در زمان نوشتن این سند: workflow کامیت شده اما **اجرا نشده** (شاخه هنوز push نشده) — نتیجهٔ اولین اجرا پس از push در worklog ثبت خواهد شد.

## ۷) قواعد نگهداری

- هر ویژگی جدید = تست قبل از پیاده‌سازی (قرمز→سبز) + ردیف وضعیت در ماتریس مربوطه.
- هر رفکور = تست‌ها سبز بمانند؛ اگر تست باید عوض شود، دلیلش در توضیح کامیت.
- پیام‌های فارسی ادعاییِ رفتاری باید از منبع استخراج شوند (اسکریپت `scripts/dotnet_resx.py`) — ترجمهٔ مجدد و «تقریباً همین» ممنوع.
- seed توسعه (`prisma/seed.ts`) و seed تست (`tests/fixtures/seed-test.ts`) عمداً جدا هستند — تست به دادهٔ دموی توسعه وابسته نیست.
- مستندسازی نتیجهٔ هر اجرا در `docs/testing/test-inventory.md` (تعداد/وضعیت) و worklog.

## ۸) تصمیمات مستند (انحرافات آگاهانه)

1. سرور تست در حالت dev اجرا می‌شود نه بیلد پروداکشن — سریع‌تر برای تکرار؛ معادل بیلد در کار جداگانهٔ `build` در CI پوشش داده می‌شود.
2. تست یکپارچه‌سازی روی HTTP واقعی است (نه فراخوانی مستقیم هندلر) چون زنجیرهٔ نشست/کوکی/گارد/مسیریابی فقط در سرور واقعی معنا دارد.
3. E2E فقط مسیرهای حیاتی را پوشش می‌دهد (ورود/نشست/دسترسی/صفحات اصلی) — پوشش صفحه‌به‌صفحهٔ کامل به فاز مقایسهٔ UI موکول است (docs/parity/ui-comparison-plan.md).

# طراحی همگام‌سازی MedPad از Ideal CRM

> سند ۱۰ — الگوی دریافت مستقل و به‌روزنگهداری دیتابیس خودِ MedPad

## ۱. هدف و اصل

MedPad نباید برای نمایش اطلاعات به Ideal وابسته بماند؛ داده را از IdealBridge **دریافت** و در دیتابیس مستقل خود **ذخیره** می‌کند. این سند قرارداد مصرف IdealBridge برای این هدف است (پیاده‌سازی سمت MedPad در پروژهٔ MedPad Integration Service انجام می‌شود — خارج از دامنهٔ این مأموریت، مطابق بخش ۴ مأموریت).

## ۲. محدودیت بنیادین: ستون «آخرین تغییر» وجود ندارد

بررسی کامل اسکیمای Ideal 3.1.18.187 (`CRMTabel.ssdl`) نشان داد:

- `CrmCompany` (۱۱۷ ستون)، `CrmCompanyPersons`، `CrmConversation`، `CrmProjects`، `CrmUserTasks`: **هیچ ستون `LastModifiedDate` ندارند.**
- `RegisterDate` = تاریخ **ایجاد** رکورد (نه ویرایش).
- `UserId` = آخرین ویراستر (بدون زمان).
- استثناها: `WSOrder.TspOrdLastEditDate` (فقط برای سامانهٔ مالیات) و `WSPreOrder.pordChangeStatusDate` — قابل‌اتکا برای آن دو موجودیت نیست و برای مشتری/شخص/مکالمه معادل ندارند.

**نتیجه:** «دریافت افزایشیِ تغییرات» به معنای دقیق کلمه از دیتابیس Ideal **ممکن نیست** — و به حکم مأموریت، هیچ دادهٔ ساختگی برای شبیه‌سازی تغییر تولید نمی‌شود.

## ۳. مدل پیشنهادی: دو لایه

### لایهٔ ۱ — دریافت جدید‌ها (افزایشی، سریع)

مشتریان/اشخاص/مکالماتِ **تازه‌ایجادشده** را با پنجرهٔ تاریخ ثبت بگیرید:

```
GET /api/v1/sync/companies?registeredFrom=2025-11-01&registeredTo=2025-11-08&limit=200
```

- با `pagination.nextAfterId` و `hasMore` صفحه‌به‌صفحه ادامه دهید.
- MedPad مسیر را ذخیره می‌کند: `lastWindowEnd` + `lastAfterId` → پس از قطع ارتباط از همان‌جا ادامه (Resume).
- شناسهٔ پایدار: `CompanyID` و همتاهایش (هرگز GUID که ممکن است در نسخه‌ها تغییر کند).

### لایهٔ ۲ — کشف ویرایش/حذف (Snapshot دوره‌ای + مقایسه)

چون زمان ویرایش در Ideal نیست، تغییر/حذف فقط با مقایسه کشف می‌شود:

1. **شناسه‌های همه:** دوره‌ای (مثلاً شبانه) کلیدها را صفحه‌بندی کنید (فقط id — سبک):
   ```
   GET /api/v1/companies?pageSize=500&afterId=0   → فقط ids
   ```
2. **مقایسه با کلیدهای موجود در MedPad:**
   - id در Ideal نیست ولی در MedPad هست → **حذف‌شده در Ideal** → MedPad تصمیم می‌گیرد (حذف منطقی/tombstone).
   - id در MedPad نیست → جدید → در لایهٔ ۱ گرفته می‌شود.
3. **تشخیص ویرایش (دقیق‌تر):** برای دیتاست‌های حساس، در چرخهٔ Snapshot کل رکورد را بگیرید و هش مقایسه کنید (IdealBridge در پاسخ رکورد کامل می‌دهد؛ MedPad می‌تواند hash رکورد نگه دارد). حجم را با `pageSize` و ساعت کم‌ترافیک کنترل کنید.
4. **نشانگرهای غیرفعال‌شدن (بدون حذف فیزیکی):** Ideal معمولاً حذف منطقی ندارد ولی این فیلدها «وضعیت» را می‌رسانند:
   - مشتری: `isDraft` (پیش‌نویس)
   - شخص: `workingOut` (خارج‌شده)
   - انبار: `deActive`
   - کاربر: `isActive`, `isActiveInWebApp/WinApp/MobApp`, `expireDate`
   - محصول: `inActive`, `inactiveInSale/Buy`
   - سفارش/پیش‌سفارش: `isVerified` (وضعیت تأیید)

## ۴. الگوی پیمایش Keyset (پیشنهادی برای همه)

```
cursor = 0
loop:
    r = GET /api/v1/sync/companies?afterId={cursor}&limit=200
    upsert(r.data)                    # با شناسهٔ پایدار — ضدتکرار به‌اصطلاح Idempotent
    cursor = r.pagination.nextAfterId
    saveCheckpoint(cursor)            # ذخیرهٔ نقطهٔ ادامه (Resume)
    if !r.pagination.hasMore: break
```

مزیت‌ها:
- **پایدار:** ترتیب `ORDER BY id` با درج هم‌زمان به‌هم نمی‌ریزد (برخلاف page عددی).
- **قابل ازسرگیری:** بعد از قطع شبکه از `cursor` ذخیره‌شده ادامه می‌دهید.
- **سبک:** هر صفحه حداکثر ۵۰۰ رکورد.

## ۵. Retry و خطا

| وضعیت HTTP | اقدام MedPad |
|---|---|
| 429 (نرخ) | صبر طبق سرنخ `Retry-After` یا backoff نمایی (۲s→۴s→۸s) و تلاش مجدد |
| 503 (دیتابیس Ideal) | عقب‌نشینی نمایی؛ آلارم اگر تکرار شد |
| 401 | توکن منقضی/ابطال — فراخوانی مدیر برای توکن جدید |
| 5xx دیگر | تلاش مجدد با backoff؛ صفحهٔ جاری از checkpoint تکرار می‌شود (upsert idempotent پس بی‌ضرر) |

**تعیین موفقیت/شکست همگام‌سازی:** هر پاسخ موفق 200 است؛ MedPad باید `pagination.hasMore` و `nextAfterId` آخرین صفحه را همراه timestamp در جدول وضعیت همگام‌سازی خود ذخیره کند:
```
sync_run(id, entity, window_start, window_end, last_after_id, status, started_at, finished_at, error)
```

## ۶. ضدتکرار

- کلید یکتای upsert در MedPad = شناسهٔ Ideal (`companyId`, `personId`, ...).
- ترتیب دریافت پیشنهادی: اطلاعات پایه → کاربران → مشتریان → اشخاص → آدرس‌ها → پروژه‌ها → مکالمات → یادآوری‌ها → محصولات → سفارش‌ها (وابستگی‌های FK به این ترتیب ارجاع برقرار می‌کنند).

## ۷. قرارهای جانبی

- **تاریخ‌ها:** همهٔ فیلترها و خروجی‌های تاریخ، میلادی ISO هستند (`yyyy-MM-dd`). تاریخ‌های شمسی نمایشی Ideal (`RegisterDatePersian`) هم در DTO هست.
- **حجم:** سقف ۵۰۰ رکورد/درخواست؛ برای Snapshot کامل، پیمایش شبانه با pageSize=500.
- **نرخ:** 120 درخواست/دقیقه با صف ۳۰تایی روی هر توکن.
- **تغییر ساختار Ideal (نصب نسخهٔ جدید):** بعد از هر ارتقای Ideal، `/health/db` را بگیرید و اگر `TablesMissing/ColumnsMissing` جدید دیدید، Snapshot کامل تکرار کنید.

## ۸. چه چیزی «تغییر» تلقی نمی‌شود (شفاف‌سازی)

- IdealBridge تغییرات را «رویداد» اعلام نمی‌کند (Webhook ندارد) — همه‌چیز Pull است.
- تشخیص «چه کسی/چه زمانی ویرایش کرد» برای مشتری وجود ندارد (`lastEditUserId` بدون زمان). اگر MedPad این را نیاز دارد، باید از سمت کاربران Ideal درخواست فعال‌سازی/Snapshot دقیق‌تر شود — در گزارش محدودیت‌ها ذکر شده.
